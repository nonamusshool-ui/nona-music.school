# НОНА Music School — правила для AI-агентів

Цей файл читають усі агенти (Codex, Claude Code та інші). Перед будь-якою задачею прочитай його повністю.
Якщо задача суперечить правилам нижче — зупинись і запитай, а не обходь правило.

## 1. Що це за проєкт

- Сайт онлайн-школи гітари НОНА: https://nonaschool.com.ua (домен задано у `CNAME`).
- **Статичний сайт без збірки.** Немає `package.json`, бандлера, фреймворку. HTML + CSS + звичайний JS (ES-модулі в кабінетах). Не додавай інструменти збірки, npm-залежності чи фреймворки без прямого дозволу власника.
- Бекенд — **Supabase** (Postgres + Auth). Вхід через Google OAuth та magic link, PKCE-flow.
- Форми заявок на `/guitar/` надсилаються через **Web3Forms** (`api.web3forms.com`).
- Аналітика — **Google Analytics 4** (`G-H3QLF10CVM`).
- Мова інтерфейсу та всіх текстів для відвідувачів — **українська**. Час занять відображається за Києвом.

## 3. Як працюємо з Git

- Одна задача = одна гілка. Працюй у своїй гілці, комміть локально.
- **У `main` потрапляє тільки за командою власника «пуш».** «Пуш» означає: злити свою гілку в `main` і запушити `main`. Без цієї команди нічого в `main` не пушити, навіть якщо задача готова.
- Перед командою «пуш» зміни мають пройти рев'ю (розділ 10). Якщо рев'ю ще не було — нагадай власнику, але остаточне рішення за ним.
- Перед злиттям у `main` підтягни свіжий `main` (`git pull`) і, якщо є конфлікти, — зупинись і покажи їх власнику, не вирішуй «на око».
- Назви гілок: `codex/<коротко-що>` або `claude/<коротко-що>`, наприклад `claude/og-image`.
- Якщо агент не має технічної можливості створити гілку або запушити — не обходь правило. Зроби локальний commit/diff і скажи власнику, що саме залишилось виконати.
- **Чіпай тільки файли, потрібні для задачі.** Не «покращуй заодно» сусідній код, не переформатовуй файли цілком — це створює конфлікти з іншими агентами, які працюють паралельно.
- Для рев'ю відкривай pull request зі своєї гілки (або, якщо PR неможливий, дай власнику diff). Опис PR / звіту обов'язково містить:
  1. Що змінено і навіщо (1–3 речення).
  2. Список змінених файлів.
  3. **Як перевірити** — конкретні кроки (сторінка, дія, що має статися).
  4. **Що фактично перевірено агентом, а що ні** (див. розділ 9). Якщо нічого не запускалось — так і писати: "Не перевірено вручну".
  5. Ризики або що свідомо не робилось.

## 4. Правила фронтенду

- **Версії кешу `?v=N`.** Змінив `.js` чи `.css` — підніми `?v=` **в усіх місцях**, де цей файл підключається (HTML і `import` у JS). Перед завершенням перевір пошуком: `grep -rn "назва-файлу.js?v=" .` — усі входження мають мати однакову нову версію.
- **Не використовуй `innerHTML`, `insertAdjacentHTML`, `document.write`, `eval`.** Текст — через `textContent`, елементи — через `createElement`. Це захист від XSS, у проєкті зараз немає жодного такого виклику — так і має лишитись.
- Мобільні — основна аудиторія (~60% трафіку). Кожну зміну інтерфейсу перевіряй на ширині 360–400 px.
- Зовнішні скрипти — тільки з закріпленою версією (як `@supabase/supabase-js@2.117.2`). Нових зовнішніх скриптів без дозволу не додавати.
- Зображення:
  - Контентні растрові зображення: переважно WebP/AVIF + `srcset`, `width`, `height`, змістовний `alt`.
  - Декоративні зображення — `alt=""`.
  - SVG/favicon/OG-зображення можуть використовувати відповідний їм формат.
- Не змінюй H1, title, meta description, canonical, robots, sitemap або structured data, якщо задача явно не стосується SEO або власник прямо це не попросив.
- Тексти для відвідувачів пишемо українською, без канцеляриту. **Ціни, телефони, умови пробного уроку й пакетів не змінюй без прямої вказівки** — це бізнес-рішення власника.

## 5. Аналітика (GA4)

Наявні події — **не перейменовуй і не видаляй**, на них зав'язані звіти й конверсія в Google Ads:

| Подія | Де | Коли |
|---|---|---|
| `trial_cta_click` | `guitar/guitar.js` | Клік по кнопці запису на пробний |
| `trial_form_open` | `guitar/guitar.js` | Відкрилась форма заявки |
| `trial_form_start` | `guitar/guitar.js` | Людина почала заповнювати форму |
| `generate_lead` | `guitar/guitar.js` | Заявку успішно надіслано (**головна конверсія**) |
| `phone_click` | `guitar/guitar.js` | Клік по номеру телефону |
| `facebook_click` | `script.js` | Клік по посиланню на Facebook |

- Події відправляй лише після перевірки `typeof window.gtag === "function"` і в `try/catch` — аналітика ніколи не має ламати сайт.
- **Жодних персональних даних у подіях** (ім'я, телефон, email, текст повідомлення).
- Нову подію додав — допиши її в цю таблицю.

## 6. Supabase (база даних)

- **Застосовані міграції не редагуй.** Будь-яка зміна — новий файл `supabase/migrations/YYYYMMDDHHMMSS_опис_англійською.sql`.
- Кожна нова таблиця: `enable row level security` + явні політики. Без RLS таблицю не створювати.
- `SECURITY DEFINER`:
  - завжди `set search_path = ''` і повні schema-qualified імена;
  - public RPC, який викликає клієнт, повинен на початку перевіряти `auth.uid()` / роль / ownership;
  - спочатку `revoke all ... from public, anon, authenticated, service_role`;
  - `grant execute` давай тільки тій ролі, яка реально повинна викликати функцію;
  - private helper-функції не відкривай `authenticated`, якщо прямий виклик не потрібен.
  - **Увага:** helper-и, які викликаються з RLS-політик (`private.current_role()`, `private.is_admin()`, `private.is_teacher_of()`, `private.is_student_of()`, `private.is_conversation_participant()`, `private.package_lessons_used()` тощо), виконуються від імені користувача, тому `authenticated` **потребує** на них `execute`. Не відкликай ці гранти — інакше RLS зламається і користувачі втратять доступ до своїх даних. Перед зміною грантів на будь-який helper перевір, чи він не використовується в політиках: `grep -rn "назва_функції" supabase/migrations/`.
- Роль користувача визначає **тільки** таблиця `profiles`. Ніколи не довіряй ролі з `user_metadata`, URL чи даних з браузера.
- Нова логіка в базі — новий тест у `supabase/tests/` за зразком наявних (випадкові фікстури, фінальний `ROLLBACK`, без реальних даних).
- Ключ `sb_publishable_...` у `supabase-client.js` публічний за задумом — це нормально. **`service_role` ключ, паролі, токени, будь-які секрети в репозиторій не додавати ніколи.**

## 7. Робота з production

- За замовчуванням будь-яка перевірка production Supabase — read-only.
- Не запускай INSERT / UPDATE / DELETE / DDL, міграції, RPC із побічними ефектами або destructive-команди без прямої вказівки власника.
- SQL-тести НІКОЛИ не запускати проти production. Тільки окрема test/branch database.
- Якщо не впевнений, чи дія змінює production data — зупинись і запитай.

## 8. Приватні та внутрішні дані

**Репозиторій публічний** — усе, що в нього потрапляє, бачить будь-хто, і з історії Git це вже не видалити.

- Внутрішню методику проведення пробного уроку не публікувати в HTML, JS, CSS, JSON-LD, коментарях, data-атрибутах чи інших файлах публічного репозиторію.
- Не додавати в репозиторій приватні email, токени, UUID користувачів, внутрішні нотатки або персональні дані учнів.
- Не логувати PII в console / analytics.
- Імена, фото та персональні профілі викладачів не публікувати без прямого дозволу власника.
- Винятки, які **вже є і є нормою**: `access_key` Web3Forms у `guitar/index.html` (публічний ключ форми за задумом) і `sb_publishable_...` у `supabase-client.js`. Нових ключів за їхнім зразком не додавати без погодження.
- Якщо секрет або персональні дані все ж потрапили в коміт — не намагайся «тихо прибрати» новим комітом, одразу повідом власника: ключ треба відкликати й перевипустити.

## 9. Готово, коли

Чесність перевірки:

- Не заявляй, що щось перевірено, якщо фактично не запускав перевірку.
- Якщо браузер / test environment недоступний — прямо напиши в PR: "Не перевірено вручну" і дай кроки для людини.
- Не надсилай тестові заявки в production і не створюй/змінюй реальні дані лише заради перевірки без дозволу власника.

Чекліст:

- [ ] Зміна робить рівно те, що в задачі, і не чіпає зайвого.
- [ ] Версії `?v=` підняті всюди, де змінений файл підключено.
- [ ] Сторінка перевірена на мобільній ширині та на десктопі, в консолі браузера немає помилок.
- [ ] Якщо зачеплено форму заявки — перевірено без реальної заявки: валідація полів, відсутність помилок у консолі, код відправки й події `generate_lead` не зламаний. Реальне надсилання робить людина з дозволу власника — дай для цього кроки в PR.
- [ ] SEO-елементи (H1, title, description, canonical, robots, sitemap, structured data) не змінені, якщо задача не про SEO.
- [ ] Якщо зачеплено базу — є нова міграція й тест, старі міграції не змінені, у production нічого не застосовано без вказівки власника.
- [ ] У змінах немає приватних даних, секретів чи внутрішньої методики (розділ 8).
- [ ] Опис PR заповнений за шаблоном з розділу 3.

## 10. Чекліст рев'ю (коли перевіряєш PR іншого агента)

1. Чи зроблено саме те, що просили, і нічого понад це?
2. Чи немає змінених файлів, які не стосуються задачі?
3. `?v=` піднятий у всіх місцях?
4. Немає `innerHTML` / нових зовнішніх скриптів / секретів?
5. Події аналітики не перейменовані, нових персональних даних у них немає?
6. Для бази: RLS, `search_path = ''`, перевірка прав, `revoke/grant`, тест?
7. Чи не робив автор PR записів, міграцій або тестів у production-базі (розділ 7)?
8. Чи немає в diff приватних даних: email, токенів, UUID користувачів, внутрішньої методики, імен чи фото викладачів без дозволу (розділ 8)?
9. Чи не змінені без запиту H1, title, meta description, canonical, robots, sitemap, structured data?
10. Чи чесно в PR сказано, що перевірено, а що ні? Твердження «перевірено» без фактичного запуску — підстава не схвалювати.
11. Чи можна перевірити зміну за кроками з опису PR?

Пиши рев'ю конкретно: файл, рядок, що не так, як виправити. Не схвалюй PR «на око».

## 11. Відомі проблеми (беклог)

- Різні версії кешу одних файлів: `guitar.css` (`v=14` на `/guitar/`, `v=12` на підсторінках), `dashboard.js` (`v=15` у кабінетах учня й викладача, `v=16` в адмінці), `cabinet.css` (`v=10` / `v=11`).
- `<script>` Google Analytics стоїть перед `<meta charset>` у `<head>` — `charset` має бути першим.
- Картинка для соцмереж `assets/school-cover.png` 960×399 і 434 КБ — потрібна 1200×630 у JPG.
- Відео `assets/videos/nona-milonga.mp4` 4,3 МБ без `poster`.
- У `_headers` немає `Content-Security-Policy`, `Strict-Transport-Security`, захисту від iframe (і невідомо, чи хостинг взагалі читає `_headers`).
- Немає банера згоди на аналітику для відвідувачів з ЄС.
- SQL-тести ніхто автоматично не запускає (немає CI).
